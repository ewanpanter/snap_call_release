# Data

`prepare.py` downloads two public datasets, maps their labels to SnapCall questions, splits
them 70/15/15 (stratified, seed 2609) and writes contract-valid `DataRecord` JSONL:

```
uv run python data/prepare.py --out outputs/data           # ~6 s, ~15 MB download
uv run python data/prepare.py --out outputs/data --full    # every record, no subsampling
```

Output: `train.jsonl`, `val.jsonl`, `test.jsonl` (both datasets in each; the `dataset` field
tells them apart) and `stats.json` (counts, label distributions per split, imbalance flags).
CI writes them to `gs://<project>-scratch/data/` with `data.yml`. The data itself is never
committed (`outputs/` and `data/raw/` are gitignored).

## Questions

**Tickets** (4 per state; state = `Subject: …` + body):

| id | type | from |
|---|---|---|
| `queue` | choice, 10 | `queue` |
| `type` | choice, 4 (incident, request, problem, change) | `type` |
| `priority` | score, 3 levels (low, medium, high) | `priority`. The card says Low/Medium/Critical; the CSV has low/medium/high. |
| `is_billing` | yesno | queue is Billing and Payments, or a tag is Billing/Payment/Refund/Invoice |

**Telco** (3 per state; state = the customer's message):

| id | type | from |
|---|---|---|
| `intent` | choice, 26 (the contract's maximum) | `intent` |
| `category` | choice, 7 | `category` (fully determined by intent) |
| `wants_to_leave` | yesno | intent is cancel_plan, change_provider, check_cancellation_fee or deactivate_phone |

## Sampling and split

- Deduplicate on normalised text (lower-case, collapsed whitespace). A text that repeats with
  different gold answers is dropped entirely.
- Default size: 750 test states from tickets and 250 from telco (1,000 in total, as in the
  plan), so the whole sample is `test / 0.15`: 5,000 tickets and 1,667 telco records. Change
  with `--tickets-test` / `--telco-test`, or use `--full`.
- Stratified on the full tuple of gold answers: records are sorted by it (random tie-break
  from the seed), sampled systematically, and assigned to splits in an interleaved 70/15/15
  pattern. The first question (queue / intent) is exactly proportional in every split; the
  others are close.

## Out-of-domain set (forgetting check)

`ood_test.jsonl` holds tasks with nothing to do with customer support, so we can tell whether
a LoRA adapter has made the model worse at things it wasn't trained on. It's never used for
training, and it's written on its own, so `train/val/test.jsonl` don't change:

```
uv run python data/prepare.py --ood-only --out outputs/data       # ~30 s
gh workflow run data.yml -f args="--ood-only"                      # -> scratch/data/ood_test.jsonl
```

| `dataset` | Source | Licence | States | Questions |
|---|---|---|---|---|
| `ag-news` | [sh0416/ag_news](https://huggingface.co/datasets/sh0416/ag_news) `70e3fa1`, `test.jsonl` (AG's News, Zhang et al. 2015) | non-commercial research use | 300 | `topic` (choice, 4: world, sports, business, sci_tech), `is_business` (yesno, 25% yes) |
| `boolq` | [google/boolq](https://huggingface.co/datasets/google/boolq) validation, via the dataset viewer's rows API (Parquet only on the Hub) | CC BY-SA 3.0 | 300 | `answer` (yesno, 62% yes): the BoolQ question about a Wikipedia passage |

The viewer API can't be pinned to a revision, so the rows are pinned by the sha256 of their
canonical JSONL. A changed upstream fails loudly. BoolQ passages that carry several questions
with different answers are dropped (395 of 3,270), as `dedupe` does for the other datasets.
Usage: score the zero-shot base and each adapter on it with `eval.run_eval --data
.../ood_test.jsonl`. A drop after LoRA is forgetting.

## CFPB held-out domain (Decision 16)

Real consumer complaints about financial products, from the CFPB Consumer Complaint Database.
No system was trained on this domain, so it's the fair "does SnapCall beat Jev?" test. It's
written on its own, so `train/val/test.jsonl` don't change:

```
gh workflow run data.yml -f args="--cfpb"     # -> scratch/data/cfpb_{train,val,test}.jsonl, cfpb_stats.json
uv run --no-sync python data/nn_baseline.py outputs/data/cfpb_train.jsonl outputs/data/cfpb_test.jsonl
```

The full preparation downloads about 37 MB, so it's easiest to run it in CI.

**Licence:** CC0 1.0. The database is a US government work in the public domain; the CFPB
publishes it under CC0. No attribution is required, but cite *CFPB Consumer Complaint
Database*.

### Source: the FOIA archive, not the search API

Decision 16 said to fetch through the CFPB's search API with filters. That's no longer
possible. The CFPB stopped publishing complaint narratives on 14 Aug 2026 and **removed them
from the database and its API on 14 Sep 2026**. The API has no narrative field any more,
`has_narrative=true` is silently ignored, and the bulk `complaints.csv` has no narrative
column. Checked on 2 Oct 2026.

The narratives now live in the CFPB's [FOIA reading room archive](https://www.consumerfinance.gov/foia-requests/foia-electronic-reading-room/cfpb-consumer-complaint-database-narratives-archive/),
as CSV exports grouped by date received. They have the same columns as the old export. We use
two of them, each pinned by sha256, so a re-export fails loudly:

| File | Rows | With a narrative |
|---|---|---|
| [`CCDB_Export_19_June_2026.zip`](https://files.consumerfinance.gov/f/documents/CCDB_Export_19_June_2026.zip) (19.6 MB) | 620,794 | 16,820 |
| [`CCDB_Export_20_July_2026.zip`](https://files.consumerfinance.gov/f/documents/CCDB_Export_20_July_2026.zip) (17.0 MB) | 672,036 | 10,002 |

The August 2026 file ends on 14 Aug and contains a single narrative, so it isn't used.

### Filters, in order (all in `cfpb_record`; skip counts are in `cfpb_stats.json`)

1. **Has a narrative.**
2. **Date received from 2026-06-01 to 2026-07-31** (inclusive). This is after every model's
   training cutoff, which limits contamination: narratives are public and may sit in
   pretraining data. It's the latest window available, since publication stopped in August.
3. **100 to 4,000 characters.** This drops about 5% of narratives. Very long ones would make
   GPU runs and Jev calls expensive.
4. **English:** dropped if Spanish function words outnumber English ones.
5. **Product maps** to a current (post-2017) product name. Older names are consolidated
   (`PRODUCT_ALIASES`); names that don't split cleanly (such as "Credit card or prepaid
   card") are dropped. Every complaint in the window already uses the current names.
6. **Issue is one of the 26 options** (after `ISSUE_ALIASES`). About 17% are dropped here.
7. **Final company response:** "In progress" and "Untimely response" are dropped, since
   neither says whether there was monetary relief.

Then deduplicate on normalised text (a text that repeats with different gold answers is
dropped entirely). Next, **remove near-duplicates**: complaints whose TF-IDF cosine is ≥ 0.8
to an earlier complaint are dropped, keeping the earliest of each cluster (`near_dedupe`).
These are mostly template letters, such as FDCPA debt-validation requests filed by many
consumers. The first version of this set had 40 test states that were near-copies of a train
state, and the nearest-neighbour lookup got them all right. Finally, **cap credit reporting at
25%** of the pool (`--cfpb-credit-cap`), and
take a stratified sample with seed 2609, using the same method as the main sets. The splits
are **3,000 train / 300 val / 1,000 test**.

The cap doesn't bind in this window. Credit reporting is about 90% of all complaints, but only
about 4.5% of those with a narrative: most credit-reporting complaints come without one.

### Questions (3 per state; state = the narrative, with the CFPB's `XXXX` redactions kept)

| id | type | from |
|---|---|---|
| `product` | choice, 11 | `Product`, in the post-2017 categories |
| `issue` | choice, 26 (the contract's maximum) | `Issue`: the 2 most common issues within each of the 11 products, plus the next 4 most common overall. The descriptions are the CFPB's issue names. Four synonymous names from other products are merged in (for example, "Closing your account" is merged into "Closing an account"). |
| `monetary_relief` | yesno, about 7% yes | `Company response to consumer` is "Closed with monetary relief" |

There's no `outcome` question, because `monetary_relief` would be derivable from
it. `timely response` and `consumer disputed` aren't used either (the second no longer exists).
`issue` isn't derived from `product`. Some issue names belong to one product, so the two
answers are correlated, and that's realistic.

### Gate: the TF-IDF nearest-neighbour baseline

`data/nn_baseline.py` (stdlib only) copies each test state's answers from its most similar
train state. Run it before anyone scores. If it comes close to the models, the set is
template-like (as telco was, at 90% fully right), and the sampling must be fixed first.

## TeleLogs: 5G root cause (Decision 17)

5G drive-test logs from the GSMA Open-Telco benchmarks. Each case is a per-second KPI table
(speed, serving and neighbour PCIs, RSRP, SINR, throughput, scheduled RBs) plus the engineering
parameters of the nearby cells. The answer is the root cause of the throughput drop.

```
gh workflow run data.yml -f args="--telelogs"   # -> scratch/data/telelogs_{train,val,test}.jsonl, telelogs_stats.json
python3 data/nn_baseline.py outputs/data/telelogs_train.jsonl outputs/data/telelogs_test.jsonl --keep-numbers
```

**Source:** [GSMA/ot-full](https://huggingface.co/datasets/GSMA/ot-full), config `telelogs`,
split `test` (864 cases, ungated). It's Parquet only, so it's read through the dataset viewer's
rows API (like BoolQ) and the canonical JSONL is pinned by sha256.

**Licence:** MIT. Keep the copyright notice when redistributing; cite *GSMA Open-Telco
LLM Benchmarks (TeleLogs)*.

**Caveat:** it's a published benchmark, so it may be in the models' training data. Present it
as a "telecom knowledge" test, not a fully held-out one.

### Question (1 per state)

| id | type | from |
|---|---|---|
| `root_cause` | choice, 8 | the source answer `C1`–`C8`, mapped to `downtilt_too_large`, `overshooting`, `better_neighbour`, `overlapping_coverage`, `frequent_handovers`, `pci_mod30_clash`, `speed_too_high`, `too_few_rbs`. The descriptions are the source's wording. |

Decision 17 says 16 root causes, but every case in the data lists the same 8, and each one is
the answer 108 times. The state is the case from `Given:` on: the cell-parameter rules, the
drive-test table and the engineering parameters. The task wording, the `\boxed{}` instruction
and the lettered `C1:`–`C8:` list are stripped, so the options come only from our prompt.

### Split by drive-test segment, not by case

The 864 cases are **108 drive-test segments × 8 variants**: each segment is edited once per
cause, so the 8 siblings share almost every number. A per-case split puts the siblings of
every test case in train: 84% of test states are then near-copies (cosine ≥ 0.9) of a train
state with a *different* answer. So whole segments go to one split (`grouped_split`, seed
2609): **75 / 12 / 21 segments = 600 / 96 / 168 cases**. Each segment holds every cause once,
so every split is exactly balanced (12.5% per cause).

### Length

Measured with the Qwen3-4B-Instruct-2507 tokenizer on the real packed prompt
(`build_prompt` + `encode_prompt`): the state alone is 1,833–2,658 tokens (median 2,165).
Packed with one option order it's 2,057–2,882 (median 2,372). With `debias="auto"` it's
2,609–3,434 (median 2,924). **Every case is over the 2,048-token packed limit.** `decide`
falls back to the cached forward, so scoring works. LoRA training at the default
`--max-tokens` would skip every case.

### Gate

`nn_baseline.py --keep-numbers` (here the numbers are the signal; words alone give every
state the same vocabulary). Run it before scoring.

## CVE advisories: severity and attack vector (Decision 17)

Red Hat security advisories for CVEs made public **1 Apr – 30 Sep 2026**, after every model's
stated training cutoff (Gemini 3.5 Flash-Lite: March 2026; Gemma 4 E4B: January 2025;
Qwen3-2507 doesn't state one). The state is the advisory text with every CVSS score, vector and
severity rating removed. The gold is the CVSS 3.1 vector Red Hat publishes for the CVE, so
the task is to work the CVSS out from the facts, not to look it up.

```
gh workflow run data.yml -f args="--cve"   # -> scratch/data/cve_{train,val,test}.jsonl, cve_stats.json, cve_raw.jsonl.gz
python3 data/nn_baseline.py outputs/data/cve_train.jsonl outputs/data/cve_test.jsonl
python data/prepare.py --cve --cve-snapshot <dir>/cve_raw.jsonl.gz   # rebuild offline from the snapshot
```

Every record's `meta.source_url` links to its advisory page. The VEX files' `legal_disclaimer` and the security-data page both state this licence. |

Cisco's site terms (https://www.cisco.com/c/en/us/about/legal/terms-conditions.html) grant only a right "to view the Site Content solely for your internal use", and each advisory's Legal Disclaimer warns that copies may lack information. `data.yml` artifacts of a public repo can be downloaded by anyone, so including Cisco text would republish it. |

### Questions (2 per state)

| id | type | gold |
|---|---|---|
| `severity` | score: low / medium / high / critical | Red Hat's CVSS 3.1 base score, in the standard bands (0.1–3.9 / 4.0–6.9 / 7.0–8.9 / 9.0–10). Red Hat's own four-level rating (Low / Moderate / Important / Critical) is a different scale; it's kept in `meta.redhat_rating` and removed from the text. |
| `attack_vector` | choice: network / adjacent / local / physical | the `AV` metric of the same vector. Adjacent and physical are rare (about 1% and 0.1%); the options stay, since knowing they're rare is part of the task. |

**Hand-check (blind, 30 states per question; reader saw only the text, then compared with gold):**

| question | result | decision |
|---|---|---|
| `attack_vector` | 28/30 right; text settles it in 19, supports a guess in 8, silent in 3 | kept |
| `severity` | 23/30 exact, 30/30 within one level | kept (an inference question: CVSS from the stated facts) |
| `needs_non_default_config` | only 6 of 30 condition-bearing advisories say whether the condition is the default (3.9% of all states mention a default) | **dropped**: not answerable |
| `affected` + a device line | Red Hat VEX justifications (`vulnerable_code_not_present`, `component_not_present`, ...) describe which product ships the code, never the configuration in the text, so there's no vendor gold. Reading the text ourselves, both device lines were unambiguous in only 18/30. | **dropped** |
| `exploited_in_wild` | 7 CISA KEV positives in the whole Red Hat + Cisco pool (0.2%) | **dropped**: too few positives to score |

### Filters and sampling (`prepare_cve`)

1. **Listing:** every Red Hat CVE with `public_date` in the window (13,479).
2. **Candidates:** 6,500 are pre-sampled from the listing, stratified on the listing's CVSS, with kernel at most 25%. Fetching every CVE's text wouldn't fit in one 30-minute CI job.
3. **Per CVE** (`cve_record`; skip counts are in the stats):
   - has a CVSS 3 vector and a score above 0
   - has a title
   - not a "duplicate assignment" or "not a flaw"
   - 200–6,000 characters after redaction
4. **Text** (`cve_state`): the title, the descriptions (repeated paragraphs collapsed), Red Hat's statement and the mitigation (not the "no mitigation available" boilerplate).
5. **Redaction** (`redact_cvss`): every sentence mentioning a CVSS vector, a metric such as `(AV:N)`, a score, or a severity rating ("rated as having Important impact", "(Chromium security severity: High)") is dropped whole.
6. **Dedup:** exact, then near-dedup at TF-IDF cosine ≥ 0.8 (Chromium and kernel texts are templated).
7. **Kernel cap:** at most 25% Linux kernel CVEs. Their states are raw commit messages: mostly local, and the hardest to answer.
8. **Split:** stratified on (severity, attack_vector), seed 2609, 3,000 / 300 / 1,000.
